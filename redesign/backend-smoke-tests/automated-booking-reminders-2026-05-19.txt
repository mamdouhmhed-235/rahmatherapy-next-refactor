ARCHITECTURE PIVOT — surfaced before any code was written
=========================================================
The BUILD plan as originally written assumed a Supabase Edge Function + pg_cron
+ pg_net. Investigation confirmed this codebase is a single Cloudflare Worker
via @opennextjs/cloudflare v1.19.4. Cloudflare Workers have first-class native
cron triggers via the `scheduled()` export. Rewriting the reminder logic in
Deno for a Supabase Edge Function + enabling two new database extensions
(pg_cron, pg_net) + duplicating the Resend SDK + setting RESEND_API_KEY in two
separate secret stores would all be unnecessary complexity for what is, on the
Cloudflare path, a small custom-worker wrapper + a Next.js API route.

The pivot was reviewed and approved by the operator before code was written.

DEPLOYMENT TARGET: Cloudflare Workers (NOT Supabase Edge Functions). Cron
trigger lands in wrangler.jsonc; scheduled() handler self-fetches the Next.js
API route via the existing WORKER_SELF_REFERENCE service binding.

OPENNEXT PATTERN CHOSEN: Pattern B — `scheduled()` does an internal fetch to
the Next.js API route `/api/cron/booking-reminders`. Reasons:
  1. WORKER_SELF_REFERENCE service binding already exists in wrangler.jsonc
     (lines 17-21) — strong signal the architecture is set up for self-calling.
  2. Cron logic lives as a Next.js API route — directly curl-testable locally.
  3. Auth gate (X-Cron-Secret header) provides clean defense-in-depth.
  4. sendBookingReminderEmail runs in its native Next.js context (no Worker /
     Deno gotchas; no template-render duplication).
  5. The custom worker wrapper is small (~80 lines) and clearly delineated.

C1 — Idempotency (dedupe)

  Source: src/app/api/cron/booking-reminders/route.ts:124-135
  Quoted block:

    // Idempotency check — has a reminder already been logged for this booking?
    const { data: existing } = await supabase
      .from("email_delivery_events")
      .select("id")
      .eq("booking_id", candidate.id)
      .eq("event_type", "booking_reminder")
      .limit(1)
      .maybeSingle();
    if (existing) {
      summary.skipped_already_sent++;
      continue;
    }

  DB cross-check: 3 booking_reminder rows in email_delivery_events from today's
  16:04 UTC invoke window. Two of those rows survive Phase D1's cleanup
  (Badar's row + the audit-seed row; the test booking's row was cascade-deleted).

  Conclusion: If the handler were re-invoked tomorrow against the same
  booking_date=2026-05-20 window, all 3 booking_ids would match the dedupe
  SELECT and be skipped before any sendBookingReminderEmail call. The
  structural guarantee is direct: an existing row → existing truthy → continue.
  No live re-invoke performed (Session 3 hard-stop in effect).

C2 — Cancellation guard

  Source: src/app/api/cron/booking-reminders/route.ts:104-122
  Quoted block:

    // Cancellation guard — fresh re-read covers the race where the booking is
    // cancelled between batch fetch and per-booking send. Belt-and-braces over
    // the IN ('pending','confirmed') filter above.
    const { data: fresh } = await supabase
      .from("bookings")
      .select("status")
      .eq("id", candidate.id)
      .single();
    if (!fresh) {
      summary.failed++;
      Sentry.captureMessage(
        `[cron/booking-reminders] booking ${candidate.id} disappeared between fetch and re-read.`
      );
      continue;
    }
    if (fresh.status !== "pending" && fresh.status !== "confirmed") {
      summary.skipped_cancelled++;
      continue;
    }

  Conclusion: Batch fetch at T0 finds bookings matching status IN
  ('pending','confirmed'); per-booking re-read at T1 catches any cancellation
  that occurred between T0 and the send call. The check is structurally
  correct: if status has shifted to anything other than pending/confirmed
  between fetch and re-read (cancelled, completed, no_show), the candidate is
  skipped before sendBookingReminderEmail is ever called.

  Note: There is also a defense-in-depth read of the broader window filter at
  lines 85-91 (the initial batch fetch already filters by status). The per-
  booking re-read is the race-window mitigation per the BUILD plan's "What
  can go wrong" section ("Booking cancelled between function start and Resend
  call").

  Live exercise of the race condition is mechanically infeasible without a
  parallel test surface (Vitest + mocked Supabase, OR a controlled-invocation
  endpoint). Per Session 2's process-note convention, code inspection is the
  accepted bar for this class of test.

C3 — Missing env-var (bonus #4 from the plan)

  Four required env vars; each has a fail-closed guard:

  Guard #1 — CRON_SECRET
  Source: src/app/api/cron/booking-reminders/route.ts:51-67
  Behaviour: if the env var is missing, the handler captures the error to
  Sentry and returns HTTP 500 with body { error: "Server misconfigured.",
  summary: emptySummary() } BEFORE any DB call. If the header is missing or
  doesn't match, returns HTTP 401 with body { error: "Unauthorized." }.

  Guard #2 — NEXT_PUBLIC_SITE_URL
  Source: src/app/api/cron/booking-reminders/route.ts:69-80
  Behaviour: if missing, captures error to Sentry with explicit message
  "NEXT_PUBLIC_SITE_URL not configured — reminder emails would carry a broken
  manage link." and returns HTTP 500 BEFORE any booking fetch.

  Guard #3 — SUPABASE_SERVICE_ROLE_KEY and NEXT_PUBLIC_SUPABASE_URL
  Source: src/lib/supabase/admin.ts:15-19
  Behaviour: createSupabaseAdminClient() throws Error("Missing
  NEXT_PUBLIC_SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY. Check server
  runtime environment variables.") at startup of the handler. The throw
  bubbles up; Next.js returns 500.

  Guard #4 — RESEND_API_KEY
  Source: src/lib/email/client.ts:26-29
  Behaviour: getResendClient() throws EmailConfigurationError("Missing
  RESEND_API_KEY.") on the first send attempt. The catch block in
  sendTrackedEmail records a failed row in email_delivery_events.

  Conclusion: All four guards fail closed with structured error capture or
  immediate throw. The send pipeline cannot reach Resend or write rows when
  any guard trips. Live exercise NOT performed (hard-stop in effect; the
  Resend API would be invoked downstream of any partially-failed run).

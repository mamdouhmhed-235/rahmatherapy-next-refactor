B2. First observation — 66s response then HTTP 500
  $ curl -sS -L -w "STATUS=%{http_code}\nTIME_TOTAL=%{time_total}s\n" \
      http://localhost:3000/sentry-test
  STATUS=500
  FINAL_URL=http://localhost:3000/sentry-test/
  TIME_TOTAL=66.496141s

  Dashboard: NO new issue.

  The 66s delay was striking. Sentry's @sentry/nextjs dev-mode source-map
  symbolication processor (devErrorSymbolicationEventProcessor.js) calls back
  to the Next.js dev server with a 3s AbortController; the processor stalls
  for many cycles, eventually times out per-frame, and only then submits the
  event. This is annoying-but-tolerable in isolation.

B3. Misdiagnosis #1 — duplicate instrumentation.ts
  Initial Glob "instrumentation.*" search did not return src/instrumentation.ts
  (which has existed since commit d50c796), so I concluded the instrumentation
  hook was missing entirely and created a root instrumentation.ts (commit
  9440eb3). On the next verification pass I noticed the duplicate and reverted
  (commit c6d795d). Discipline note: verification-before-completion miss; the
  Glob result should have been cross-checked with an ls of src/ before

B4. Misdiagnosis #2 — symbolication deadlock blamed as root cause
  After confirming the file structure, I diagnosed the 66s delay as the root
  cause for events not reaching Sentry (theory: AbortController + Turbopack +
  async-context interaction was breaking the post-symbolication send).
  Recommended pivot: ship with PASS-WITH-CAVEAT, document the dev-mode
  blocker, defer real verification to Cloudflare deploy.

  Operator pushed back: "the diagnosis may be incomplete and there's a
  documented workaround worth trying." Web research surfaced
  getsentry/sentry-javascript#18871: "makeNodeTransport silently drops
  server-side events with Next.js 16 + Turbopack." Root cause: the default
  transport uses Node http.request + a stream pipe inside a suppressTracing()
  wrapper; that wrapper manipulates OpenTelemetry async context, which
  interacts badly with Turbopack's async-context handling — stream callbacks
  never fire and events are silently dropped despite captureRequestError +
  onRequestError running and Sentry's ingest returning 200 OK on the direct
  envelope POST tested in A3.

  Workaround posted in the issue: replace makeNodeTransport with a custom
  transport that uses Node 18+ native fetch() instead of http.request.

  Discipline note: this operator-led course-correction prevented shipping
  a real production-blocking bug behind a "deferred" verdict. Memorialized.

B6. Apply #18871 workaround — first try, HTTP 400
  Added makeFetchTransport to sentry.server.config.ts, passing
  `transport: makeFetchTransport` into Sentry.init. The function as posted in
  the issue thread passes `headers: options.headers` straight to fetch().

  After dev restart (with `.next/` wipe), curl response time dropped from 66s
  to ~0.8s — confirms the symbolication delay was an *additional* dev-mode
  symptom, not the actual transmission blocker. But dashboard still showed
  no event. Dev console showed:
    Sentry Logger [warn]: Sentry responded with status code 400 to sent event.

B7. Diagnose the 400 — Content-Type missing in fetch() call
  Added two diagnostic console.log lines inside makeFetchTransport:
    [sentry-transport] options.headers (no Content-Type detected): {...}
    [sentry-transport] 400 response body: {...}

  Result: options.headers contained only { 'user-agent':
  'sentry.javascript.nextjs/10.51.0' }. No Content-Type. Sentry's
  makeNodeTransport sets Content-Type at the body-write step (not in
  options.headers), so the #18871 workaround as posted produces a request
  with no Content-Type header, and Sentry's ingest rejects the envelope.

  Fix: explicitly add "Content-Type": "application/x-sentry-envelope" in
  the fetch() headers object, alongside the spread of options.headers.
  This Content-Type addition is NOT in the originally-posted #18871
  workaround — it's our extension and is required for the workaround to
  actually function. Worth recording in case the #18871 workaround is
  ported to other projects.

B8. Apply Content-Type fix — second try, HTTP 400 again (but different)
  After the Content-Type fix + dev restart + .next/ wipe:
    [sentry-transport] 400 response body: {"detail":"invalid event envelope",
      "causes":["invalid envelope header","invalid value: string
      \"[Filtered]\", expected an event identifier at line 1 column 24"]}

  This was the smoking gun. "[Filtered]" is the literal sentinel string used
  by our PII scrubber at src/lib/observability/sentry-scrubbing.ts. The
  envelope header's `event_id` field had been replaced with "[Filtered]" —
  our own scrubber was corrupting Sentry's protocol fields.

B9. Diagnose the scrubber over-redaction
  LONG_TOKEN_PATTERN in sentry-scrubbing.ts:
    /\b(?:eyJ[A-Za-z0-9_-]+|[A-Za-z0-9_-]{24,})\b/g

  This is designed to catch long opaque tokens (API keys, JWTs). But a
  Sentry event_id is a 32-char hex string (e.g.,
  43752b92c1b022989e0045e6031f55c1) which exactly matches
  `[A-Za-z0-9_-]{24,}`. When scrubValue walks the captured event, it sees
  key="event_id", value="<32-char hex>", runs redactText (because event_id
  is not in SAFE_USER_KEYS or SAFE_CONTEXT_KEYS and the key name doesn't
  match the SENSITIVE_KEY_PATTERN), LONG_TOKEN_PATTERN matches the value,
  and the value is replaced with "[Filtered]". The SDK then serializes the
  envelope with `{"event_id": "[Filtered]", ...}` in the header.

  This affected EVERY captured event, not just our smoke test. The bug
  was masked by:
    (a) the makeNodeTransport + Turbopack deadlock (B4) — no event ever
        reached Sentry, so the corrupted envelope header was never
        evaluated by ingest;
    (b) the manual envelope POST in A3 bypassed the SDK entirely, so the
        scrubber never ran on it.
  With the transport fix in place, the scrubber bug becomes the next
  blocker. It is a real production bug — production deploys would have
  every Sentry event silently rejected with HTTP 400.

B10. Apply scrubber fix
  Added SAFE_SENTRY_KEYS to sentry-scrubbing.ts covering the Sentry envelope
  + event protocol fields that must pass through the scrubber unchanged:
    event_id, trace_id, span_id, parent_span_id, timestamp, platform, level,
    environment, release, dist, logger, server_name, type.
  In scrubValue's string branch, short-circuit BEFORE running the
  SENSITIVE_KEY_PATTERN check + redactText:
    if (SAFE_SENTRY_KEYS.has(key)) return value;
  Same pattern as the existing SAFE_USER_KEYS / SAFE_CONTEXT_KEYS
  exclusions. Surgical: protocol fields pass through unchanged, all other
  fields (message, tags, breadcrumb data, etc.) still scrub as before.

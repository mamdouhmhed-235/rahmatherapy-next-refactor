------------------------------------------------------------------------------
DIAGNOSIS — codebase convention check
------------------------------------------------------------------------------

Hypothesis: the original migration omitted `GRANT SELECT ... TO authenticated`,
which would explain both 2b (denial via privilege check) and 2c (failure to read
despite passing RLS predicate). The codebase pattern needed checking — is
GRANT-to-authenticated the convention, or does the codebase route all reads via
service_role?

Query:
  SELECT table_name, grantee, string_agg(privilege_type, ', ' ORDER BY ...) AS privileges
  FROM information_schema.role_table_grants
  WHERE table_schema='public'
    AND grantee IN ('authenticated', 'anon', 'service_role')
    AND table_name IN ('permissions','roles','bookings','clients',
                       'email_delivery_events','business_settings',
                       'email_template_overrides')
  GROUP BY table_name, grantee
  ORDER BY table_name, grantee;

Result (relevant columns; per table, authenticated and service_role privileges):

  Table                       authenticated                          service_role
  ---------------------------  ------------------------------------  ------------------------------------------------
  bookings                     SELECT                                DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
  business_settings            SELECT                                INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
  clients                      SELECT                                DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
  email_delivery_events        REFERENCES, SELECT, TRIGGER, TRUNCATE DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE
  permissions                  SELECT                                REFERENCES, SELECT, TRIGGER, TRUNCATE
  roles                        SELECT                                DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
  email_template_overrides     REFERENCES, TRIGGER, TRUNCATE          DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
  (initial — defect)           (no SELECT — defect)                   (correct)

Conclusion: every existing table grants SELECT to authenticated; none grant
INSERT/UPDATE/DELETE. The codebase pattern is reads-via-authenticated-with-RLS
+ writes-via-service-role-from-server-actions (so server actions preserve
audit-log writes). My new table was the ONLY one without `SELECT to authenticated`
— an inconsistency that broke the SELECT policy in practice.

FOLLOW-UP FIX
------------------------------------------------------------------------------

File:  supabase/migrations/20260519121000_email_template_overrides_authenticated_select_grant.sql
Body (one functional line, plus header comment):

  grant select on public.email_template_overrides to authenticated;

Applied via mcp__supabase__apply_migration with name
"email_template_overrides_authenticated_select_grant" — returned {"success":true}.

INSERT/UPDATE/DELETE grants to authenticated were NOT added. They remain
absent so mutations continue to require service_role, which keeps audit-log
writes routed through server actions. The INSERT/UPDATE/DELETE RLS policies
remain in the table as defense-in-depth.

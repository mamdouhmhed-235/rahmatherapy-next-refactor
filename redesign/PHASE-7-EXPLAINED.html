Phase 7 — The Pre-Ship Gauntlet Plain-English walkthrough of the admin recipe's final QA phase

Phase 7 is the final quality check before the redesigned admin can ship. You don't redesign anything new here — you stress-test what Phase 6 already built and prove that every page is equal-or-better than the baseline you captured back in Phase 2.

The 30-second version

  1. You're not building anymore. Phase 6 finished the pages. Phase 7 only audits, fixes leftover issues, and proves nothing got worse.
  2. It's a series of "gates" (10 of them). Each gate is one Claude Code command + one prompt to capture the result.
  3. 7 gates always run. 3 gates (optimize / adapt / onboard) only run if Gate 1's audit flagged that kind of problem.
  4. Each gate writes one file into /redesign/ as evidence. By the end you have FINAL-AUDIT.md, FINAL-CRITIQUE.md, and FINAL-REPORT.md.
  5. You hit STOP between gates. Review what the AI just did, approve, then run the next gate.
  6. Time budget: ~30-60 minutes of your time + AI runtime.

The mental model — why this phase exists

In Phase 6 you redesigned pages one at a time. Each page got its own focused review. But "every page is good on its own" isn't the same as "the whole admin is shippable." Phase 7 zooms out:

Compare to baselineThe scores you captured in Phase 2 are the floor. Every dimension (a11y, performance, responsiveness, theming, anti-patterns) must equal or improve.
Find what slipped throughSite-wide audits catch things per-page reviews miss: inconsistent spacing, copy drift, broken nav, missing focus rings.
Run the named gauntletThe Impeccable docs prescribe a fixed sequence: audit → clarify → harden, then polish last. The recipe follows that order exactly.
Generate paper trailEach gate produces a markdown file. That's your evidence the redesign improved things — needed for stakeholder sign-off.

The repeating pattern. Almost every gate works the same way:
  1. Type the green /impeccable … command into Claude Code. Wait for it to finish.
  2. Paste the yellow "framing prompt" from the recipe. This tells Claude to save the output to the right file, compare against baseline, and stop for your review.
  3. Review. Read the diff or report. Approve or reject before moving on.
Once you see this pattern once, every gate is the same shape — just different commands and different output files.

Step-by-step — every gate explained

↻
Handoff: Phase 6 → Phase 7
~5 minrequired
What it is
Close your current Claude Code session and open a brand-new one. Then paste the "re-prime" block from the recipe as your first message.
Why
Phase 7 judges the WHOLE site equally. A fresh session resets the AI from "still thinking about the last page I built" to "judging everything against the baseline."
What you do
  1. Confirm every Phase 6 checkbox is ticked (all pages approved, scores logged, etc.)
  2. Open a fresh Claude Code session.
  3. Paste the re-prime prompt. Claude reads 7 baseline files and summarises them back to you.
  4. You reply primed — go only after the summary looks right.
Expected outcome
AI confirms the baseline scores it must beat and the page count. You're ready to open Gate 0.
0
Gate 0 — Production Readiness Re-check
always runs
What it does
Re-verifies the backend foundations that couldn't be tested in Phase 0 (because the redesigned site wasn't running yet).
Checks
  • Every BLOCKS-REDESIGN item is in HANDLED state (not just planned).
  • Error tracking actually fires (trigger a test error → confirm Sentry receives it).
  • Backups actually restore (test-restore in the last 24h).
  • Transactional email actually sends (trigger a password reset → check inbox).
Expected outcome
A "## Production Readiness Re-check" section appended to FINAL-REPORT.md with pass/fail per item. If anything fails — STOP, don't proceed.

Gate 1 — Audit (the canonical first step)
/impeccable audit adminalways
What it does
Re-scores implementation quality across every redesigned admin page on 5 dimensions: Accessibility, Performance, Theming, Responsive, Anti-patterns.
Why it's first
Its output decides which of the conditional gates (4, 5, 6) need to run. Everything else routes off this report.
Output file
/redesign/FINAL-AUDIT.md
Expected outcome
Every dimension score is ≥ baseline. Findings get routed by severity:

P0 a11yfix NOW, before Gate 2
Copy issuesGate 2 (clarify)
Empty / error / loading gapsGate 3 (harden)
PerformanceGate 4 (optimize)
ResponsiveGate 5 (adapt)
Weak empty statesGate 6 (onboard)
Visual / token driftGate 7 (polish)
2
Gate 2 — Clarify (rewrite copy where it failed)
/impeccable clarify [page]always (per-page)
What it does
Improves copy on the six writing surfaces — labels, buttons, errors, empty states, tooltips, confirmations — but ONLY on pages Gate 1 flagged.
Why per-page
Phase 6 already approved per-page copy. A site-wide re-clarify could silently regress voice. So Gate 2 reads the audit, builds a list of just the flagged pages, and you process them one at a time.
What you do
  1. Paste Gate 2a — Claude reads the audit and gives you a list of /impeccable clarify [slug] commands.
  2. For each command: type it, wait for the diff, paste Gate 2b framing, review the diff, approve or reject.
  3. If NO pages were flagged, skip the whole gate.
Output file
/redesign/CLARIFY-PASS.md — every approved before/after diff
Expected outcome
Voice now matches PRODUCT.md's Brand Personality on every flagged page. No generic "Submit" buttons. Errors don't blame the user.
3
Gate 3 — Harden (stress-test reality)
/impeccable harden adminalways
What it does
Looks at the messy edges: empty lists, error states, loading skeletons, overflow on long names, what happens when a server call fails, what 60-character user names do to your table layout.
Two parts
Part A — Run the command. Harden returns a recommendations report (and sometimes code).
Part B — You (or Ralph) walk through HARDEN-PASS.md page-by-page and actually write the empty / error / loading state code.
Output file
/redesign/HARDEN-PASS.md — recommendations + which got implemented
Verification
Spot-check 3 pages with extreme test data (empty lists, huge names, server errors). Every state must render cleanly.
Expected outcome
The empty/error/loading gaps Gate 1 flagged are closed. Pages don't blow up on weird data.
4
Gate 4 — Optimize (performance)
/impeccable optimize adminconditional
SKIP IF
Gate 1's Performance score is ≥ 3 AND no page's LCP exceeded 2.5s.
What it does
Fixes UI performance issues: LCP, INP, CLS, render efficiency, animation jank, image weight, bundle size.
Output file
/redesign/PERF-REPORT.md — before/after metrics per page
Expected outcome
Every metric improved or held. No regressions. A list of what changed (lazy-loaded images / removed bloat / etc).
5
Gate 5 — Adapt (responsive)
/impeccable adapt admin for mobile and tabletconditional
SKIP IF
Gate 1's Responsive score is ≥ 3 AND no mobile QA issues were found.
What it does
Fixes responsive breakage across mobile / tablet / desktop without removing features for "convenience."
Verification
Playwright screenshots at 375×812 (phone) and 768×1024 (tablet). No horizontal scroll, no clipped UI, every primary action still reachable.
Output file
/redesign/ADAPT-PASS.md — change log by page and breakpoint
Catch
If pages changed significantly, re-run Gate 3 (harden) on those specific pages — responsive changes can reveal new edge cases.
6
Gate 6 — Onboard (first-run / empty states)
/impeccable onboard admin for new staff membersconditional
SKIP IF
Gate 1 didn't flag weak empty states AND PRODUCT.md doesn't mention new-staff onboarding.
What it does
Improves the first-time-user experience: useful empty-state CTAs (not just "No data"), orienting first-run screens, helpful next-steps.
Two parts
Part A — Run the command. Onboard returns design recommendations (and sometimes code).
Part B — Walk through ONBOARD-PASS.md page-by-page and write the actual empty-state code per recommendation.
Output file
/redesign/ONBOARD-PASS.md
Don't do
Don't add a tour overlay unless PRODUCT.md explicitly asked for one.
7
Gate 7 — Polish (the final detail pass — ALWAYS LAST)
/impeccable polish adminalwayslast code change
What it does
Catches the small stuff: alignment drift, spacing inconsistencies, missing hover/focus states, copy-tone misalignment. Polish refines what exists — it does not redesign.
Why last
If optimize / adapt / onboard changed the layout, polish has to clean up after them. Running polish earlier would mean re-doing it.
Output file
/redesign/POLISH-PASS.md — alignment fixes, interaction states added, copy tightening
Spot-check
3 pages — focus rings on every interactive element, hover states feel intentional, spacing rhythm is consistent.
Regression rule
Polish must NOT restructure layouts. If it did, that's a bug — revert and re-run with the constraint "alignment and consistency only."
Important
This is the last command that mutates admin code. Gates 8 and 9 are verification only.
8
Gate 8 — Critique (design quality re-score)
/impeccable critique adminalways
What it does
Re-scores design quality on the 10 Nielsen heuristics + the "AI-slop" verdict. Compares to BASELINE-CRITIQUE.md.
Output file
/redesign/FINAL-CRITIQUE.md
Expected outcome
Every heuristic score ≥ baseline. AI-slop verdict is "pass" (or at minimum, not regressed). If anything regressed, fix it before sign-off.
Re-cycle rule
If critique flags STRUCTURAL issues (broken hierarchy, anti-patterns) → re-run harden (or the relevant conditional gate), then re-run polish.
If critique flags only AESTHETIC issues (alignment, spacing) → polish handles them in place.
Limit: don't re-run polish more than once per page.
9
Gate 9 — Cross-checks (Playwright + DevTools)
alwaysmanual + automated
What it does
The hands-on verification pass — no AI commands here, you and Claude execute scripted checks together.
Playwright checks
  • Click through every admin page using only nav links — no dead links, active state highlights correctly.
  • Screenshot every page at 1440×900 and 375×812 — compare visually to baseline.
  • Test the 3 most-used forms end-to-end (happy path, empty submit, invalid data).
  • Mobile drawer/hamburger works at 375px.
Real-device tests
(required)
Real iPhone Safari + real Android Chrome. Mac WebKit ≠ iOS Safari. Document device + OS in the final report.
Assistive tech
(required)
VoiceOver / NVDA pass on the 3 most-used pages. Keyboard-only test on every form (Tab order, Enter submits, Esc closes, no traps). Admin users live on the keyboard — failure here is a P0.
Network-flaky tests
(required)
Throttle to Slow 4G, kill Wi-Fi mid-submit, force a 502 response — UI must surface a recoverable error, not silent failure.
DevTools console
Zero NEW console errors vs BASELINE-ISSUES.md on every page.
A11y stats
Alt-text coverage ≥ baseline, form-label coverage ≥ baseline, no new heading-hierarchy regressions, no new keyboard traps.
✓

always

How to actually run Phase 7, step by step

ℹ
The recipe is designed for one person sitting in front of Claude Code with a copy of the recipe HTML open. Here's the practical loop you'll repeat for every gate:
  1. Open the gate's card in the recipe HTML.
  2. Read the "What this command does" note — 2 sentences, sets your expectation.
  3. Type the green command (e.g. /impeccable audit admin) into Claude Code. Wait for it to finish.
  4. Copy the yellow framing prompt from the recipe and paste it into Claude Code.
  5. Wait for Claude to report back — it will save the output file, summarise the findings, and stop.
  6. Open the output file in /redesign/ and skim it. Spot-check Claude's claims.
  7. If something looks wrong — push back. Don't approve a regression just to move on.
  8. If everything checks out — move to the next gate.
  9. For conditional gates (4, 5, 6) — check the SKIP IF rule first. If it applies, skip and note "skipped" in the report.

Common gotchas — read before you start

Don't skip the fresh sessionPasting the re-prime into your old Phase 6 session is a known trap. The AI will be biased toward "the last page I built" instead of judging the whole site.
Polish doesn't redesignIf polish restructures a layout, that's a bug. Revert and re-run with "alignment only" constraint.
Conditional means conditionalIf Gate 1's performance score is fine, don't run optimize "just in case." Every gate that fires writes to admin code — fewer gates = less risk.
"Equal-or-better" is the barIf even one dimension regressed vs baseline, you don't ship. You go back and fix it.
STOP between gatesThe pause icons in the recipe are there for a reason. Skipping the review step is how regressions sneak through.
Real devices, not just emulationGate 9's iPhone + Android requirement is non-negotiable. Mac WebKit renders differently from iOS Safari.

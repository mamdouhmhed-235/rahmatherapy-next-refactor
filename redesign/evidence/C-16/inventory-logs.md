## 2. `audit/queries.ts` — the house reference pattern, documented precisely

**File:** `src/app/admin/audit/queries.ts`. **DO-NOT-TOUCH per dispatch — read for documentation only.**

- **Cursor shape:** `AuditCursor = { created_at: string; id: string }` — a **compound tuple**, not an opaque string/token (`queries.ts:35-38`).
- **Sort:** `ORDER BY created_at DESC, id DESC` (`queries.ts:106-107`) — the `id` tiebreak makes the cursor stable when multiple rows share a `created_at` timestamp.
- **Cursor predicate:** `created_at < cursor.created_at OR (created_at = cursor.created_at AND id < cursor.id)`, expressed via Supabase `.or()` with an embedded `.and(...)` (`queries.ts:152-156`). This is a **strictly-forward, one-directional** predicate — there is no reverse/"give me the page before this cursor" variant implemented anywhere in the file.
- **"Has more" detection:** `rows.length === AUDIT_PAGE_SIZE` (i.e., a full page came back) ⇒ `nextCursor = { created_at: last.created_at, id: last.id }`; otherwise `nextCursor = null` (`queries.ts:163-168`). There is no separate/second query (no `count`) — the "more exists" signal is inferred from page fullness.
- **How "Prev" works today: it doesn't.** There is no Prev anywhere in the shipped UI. `AuditLoadMoreButton.tsx` (`src/app/admin/audit`) keeps a single forward `cursor` in `useState` (line 30) and a `rows` array that only ever grows via `setRows(prev => [...prev, ...page.rows])` (line 40). Once a cursor advances, the previous cursor is discarded — there is no client-side history stack, and the query layer offers no backward traversal to reconstruct one query-side.
- **Filters compose cleanly:** every `AuditFilterStrip` control (`AuditFilterStrip.tsx`) submits via `router.push` to a brand-new URL, which re-runs `AuditPage` from scratch with `cursor: null` (`page.tsx:101`). There is no explicit "reset to page 1" needed because there is no page-number state at all — a filter change is indistinguishable from a fresh page load. This is the correct, simple behavior and composes fine with cursor mode.

### What `PaginationBar`'s cursor mode must be able to express
1. A **cursor value that is a small JSON object**, not a string — the bar's cursor-mode prop types can't assume `string | null`; they need to carry (or accept a serialized form of) `{ created_at, id }` without coupling to audit specifically.
2. **No total** — render "Showing N most recent" / "N matching events", never "X–Y of Z" (already correctly scoped in brief §5.7).
3. **"Has more" as a single boolean/nullable-cursor signal** (`nextCursor !== null`), not a count comparison.
4. **A decision the brief has not actually made yet** (see §5): does cursor mode mean true replace-on-navigate Prev/Next (what §4's layout sketch and §5.7's wording imply), or does it mean today's forward-only accumulate-on-click Load More (what's actually shipped)? These are different UI contracts and the bar can't "support both" for free — picking the former for audit means changing `AuditLoadMoreButton.tsx`/`page.tsx` (allowed — only `queries.ts` internals are off-limits), not just wrapping the existing button.

## 3. Operations — what Phase D Step 11's HARD-STOP decision needs

- **What the surface is for:** "Production support events. Safe metadata only: no request bodies, no health notes, no secrets, no email bodies" (`page.tsx:169`) — an internal ops/support triage queue (cron failures, degraded sends, etc.), distinct from the audit log (human admin actions) and distinct from the email delivery log (per-message provider status).
- **Who reads it:** access-gated to "the owner and practice manager" only (`getAdminPageAccess(profile, "operations")`; denial copy at `page.tsx:49-54`). Not a general-staff surface.
- **Do old rows have value?** Partially, and the UI itself signals this: the Resolved column's own description reads *"Closed. Stay on the audit log for the record"* (`operations-board.tsx:52`) — i.e., the product already treats the audit log as the durable long-term record and operations as the working queue. However, `updateOperationalEventStatus` (`operations/actions.ts:58-65`) only writes an audit_logs row recording that a **status transition** happened (`action_type: "operational_event_status_updated"`, with before/after snapshots of the operational_events row) — the *original* event's `event_type`/`summary`/`safe_context` (why the event fired in the first place) is **not** independently duplicated into audit_logs. So once a row ages past the 300-cap, the transition history survives in the audit log, but the original diagnostic detail (what actually happened, its safe_context payload) does not. That is a real, non-cosmetic loss for anyone trying to investigate an old incident after the fact.
- **Does anything deep-link to a specific old row?** No. Grepped every reference to `/admin/operations` across the codebase (nav, dashboards, reports, cron route comments) — every single link points at the page root or at filter query params (`?severity=error&status=open#operations-panel-open`), never at a specific event id or a `/admin/operations/[id]` route (no such route exists). **Conclusion: an unreachable old row is inconvenient, not a broken link** — nothing external depends on a specific row's URL.
- **Practical implication for the Owner's choice:** since nothing links to individual rows and the audit log already carries the transition trail, "documented cap is correct" is a defensible verdict IF the safe_context/original-event detail loss is accepted as tolerable. If the Owner wants old incident detail retrievable, a pager (page size 100, per brief §2.4) is the safer choice — the query layer is already pagination-ready (`limit`/`offset` params exist unused, `operations-data.ts:56-59,73-74`, plus an unused `countOperationalEvents()` head-count helper at lines 109-123).
- **The nested client-side "Load more" is a separate, smaller issue:** even if Phase D ships a real server pager, `OperationsBoard`'s per-column `pageSize`/`DEFAULT_PAGE_SIZE=50` reveal-more-of-what's-already-fetched pattern (`operations-board.tsx:63-77,296-298,386-399`) still exists underneath it and will need to be reconciled with (or replaced by) whatever the shared bar does, since today it's a second, independent pagination mechanism layered on top of the outer 300-row cap.

## 4. Email templates / studio — static or growing?

Confirmed **static-by-nature**, and the "16 templates" figure in my dispatch is **refuted**: the registry (`src/app/admin/emails/components/templates-data.ts`) currently defines **18** templates (its own header comment at line 1 says "the 18 templates exposed by src/lib/email/templates.ts"; I independently counted 18 `id:` entries in the `TEMPLATES` array, lines 557-890). It has grown from whatever baseline via C-01 (+1: `review_request_client`... actually most were pre-existing; C-01/C-02/C-08/C-15 each added 1-3 over time), and will keep growing slowly as new notification types ship — but:
- No query, no table — it's a compiled TypeScript const array. Rendering cost is O(18), not O(rows-in-a-table).
- `TemplateGallery` already groups by audience (`customer`/`staff`/`admin_internal`, 3 sections) — exactly the "structure, not pagination" treatment C-16 §2.5 prescribes for static-but-sprawling lists, and it's already shipped (C-15 Phase E), not something C-16 needs to add.
- The one live query in this area (`getTemplateOverrideSummaries`, `src/lib/email/templates.ts:754-785`) is unbounded but inherently small: its row ceiling is (template count × editable-field count per template), not a time-series log — even at 18 templates × ~5 fields it's under 100 rows, forever.

**Verdict: already-correct.** No pagination or further structural work needed here; flag the "16 vs 18" discrepancy to whoever wrote that figure into the dispatch.

## 5. Audit claims found WRONG at today's HEAD (74ed6ed)

1. **Brief §5.7 / dispatch framing — "Cursor-mode surfaces (audit log): no total readout; Prev/Next tokens only — already the shipped behaviour."** This is **false as written**. The shipped behaviour is a single forward-only **"Load more" append button** (`AuditLoadMoreButton.tsx`), not a Prev/Next pair. There is no Prev control anywhere on `/admin/audit`, and clicking "Load more" repeatedly **accumulates** rows in the DOM (`setRows(prev => [...prev, ...page.rows])`) rather than replacing the visible page — i.e., the audit log's own UI is the exact unbounded-DOM-growth "Load more" pattern that brief Q9.3 explicitly rejects for the rest of the app ("unbounded DOM growth on long sessions recreates the endless-scroll problem the user named"). The **query layer** (`fetchAuditPage`, cursor-based, page size 100) is sound and correctly described; the **UI layer** built on top of it is not what "Prev/Next tokens" implies. This matters directly for Phase B: the shared `PaginationBar`'s cursor mode cannot simply "match already-shipped behaviour" — shipped behaviour and the brief's own Q9.3 locked decision are in tension with each other on this one surface.
2. **A closely related, previously-unflagged gap:** day-group headers (`dayKey`/`dayLabel` bucketing) are applied **only** to the initial server-rendered page (`DayGroupedTimeline`, `page.tsx:236-293`) — every batch loaded via "Load more" renders as a **flat, ungrouped list** (`AuditLoadMoreButton.tsx:49-65`). This is a live, shipped instance of exactly the "date-group split across a page boundary" subtlety the dispatch asks about for the emails delivery feed (§2 above / assignment item 2) — except here it's not a hypothetical risk of a future pagination conversion, it's the **current, already-live** behavior of the one surface the brief calls "done right."
3. **Template count:** not from the 2026-07-16 audit itself, but the dispatch's own "16 templates is static-by-nature — confirm or refute" is refuted: it's **18** at HEAD (see §4). Flagging since the dispatch explicitly asked to check it.

No other claims in my scope (emails-100-cap-no-pager, operations-300-cap-no-pager) needed correction — both are still accurate at HEAD despite the heavy C-08/C-09/C-15 churn in these directories; C-09 added real server-side *filtering* to both surfaces but did not add pagination (the pagination-ready `limit`/`offset` params and the head-count helpers were added in anticipation of C-16 and are explicitly noted as "not called by the page today" in both `emails-data.ts` and `operations-data.ts`).

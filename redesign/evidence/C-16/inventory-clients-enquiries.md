## Extra-depth findings

### 1. The client→bookings map — can it be built per-page, or does the UI need aggregates across all clients?

**Not reducible to per-page without restructuring.** The unbounded `bookings` fetch (`clients-list-data.ts:146-151`) feeds `bookingsByClientId`, which `page.tsx` uses for four purposes:

- **(a) Filtering** — `matchesFilters` (lifecycle/payment/source/location, `:214-269`) runs on `clients` (the full deleted-scoped set) **before** the 50-row slice (`visibleClients` at `:361`, sliced later at `:429`). Lifecycle/payment/source classification is derived from a client's *entire* booking history. If the clients query were simply `.range()`'d to fetch only one page of clients, and bookings were fetched only for those client IDs, filtering would only ever see one page's worth of clients — wrong for e.g. "show all at-risk clients."
- **(b) Sort** ("last_visit") — same issue: sorting must happen across the whole filtered set before slicing, and "last visit" needs each client's latest completed booking, i.e. full booking data (or a materialized `last_visit_date`) for every client, not just the current page.
- **(c) Stats line** (`activeCount`/`newThisMonthCount`/`returningCount`/`atRiskLapsedCount`, `page.tsx:443-454`) is computed over `clients` (the full deleted-scoped list), **not** `pageRows` — a page-wide aggregate that can never be satisfied by "just this page's bookings."
- **(d) Per-row display** (timeline, count label) — this part genuinely only needs the current page's clients' bookings and could be served by `bookings.in("client_id", pageClientIds)`.

So (d) is page-friendly; (a)/(b)/(c) are not, without moving lifecycle/last-visit classification into SQL (a computed column/view — likely conflicts with the brief's "zero migrations" promise, §6) or building a **separate, slim aggregate query** (per client_id: last-completed-date, next-upcoming-date, completed/upcoming counts, outstanding balance, source set) that runs once against the whole `clients`⋈`bookings` join without transferring full booking row payloads — cheaper than today's full-row fetch, but still a new query shape, not a copy-paste `.range()`. **This confirms the assignment's premise: Phase C Step 8 for clients is not simple.** The existing `countClients()` companion (`:170-186`) only takes an `includeDeleted` boolean — it cannot answer "how many clients match lifecycle=at_risk," so even the pagination-ready count helper doesn't solve the aggregate problem.

### 2. C-06's deleted-clients toggle — how does it enter the query? Compose with `.range()`?

It **does not enter the query at all today.** `clients-list-data.ts`'s clients query (`:135-138`) has no `.is("deleted_at", null)`/`.not(...)` of any kind — every load fetches live *and* soft-deleted clients unconditionally. The "Show deleted" toggle (`page.tsx:344-349`, `showDeleted ? allClients : allClients.filter(c => !c.deleted_at)`) is a pure in-memory JS filter applied *after* the fetch.

This does **not** compose cleanly with `.range()`: if the clients query were paginated at the SQL level while the deleted-filter still ran in JS afterward, a raw page of N rows could yield fewer than N visible rows (or an apparently-empty page while more live clients exist further in the range) — count/page math would drift. The fix mirrors what `countClients(includeDeleted)` already does correctly (`:170-186`, conditional `.is("deleted_at", null)`): the main query needs the same conditional predicate pushed into SQL, at which point the toggle becomes a real filter param and composes fine with `.range()`.

### 3. The `[clientId]` detail page rails, and `PRIVACY_NOTES_LIMIT`

Rails inventoried individually in table rows 3–6 above. On `PRIVACY_NOTES_LIMIT` specifically: **confirmed** — `PRIVACY_NOTES_LIMIT = 25` (`src/app/admin/privacy/privacy-data.ts:44`, used at `:159`) bounds the **system-wide sensitive-notes rail on `/admin/privacy`** (`.eq("is_sensitive", true)` across *all* clients, capped at 25). It has nothing to do with `/admin/clients/[clientId]`. The `[clientId]` detail page's own Notes rail (`client-detail-data.ts:342-350`, scoped `.eq("client_id", clientId)`) has **no limit of any kind** — not 25, not anything — a distinct, separately-unbounded surface that the pre-flight prep's privacy/emails-focused correction didn't cover. Flagging it here as a finding specific to this scope.

Also of note: the LTV ribbon (`ClientLtvRibbon.tsx`) and `StatsPanel`'s totals (total spend, common services, visit counts) consume the *same* `bookingHistory` array as the tabbed booking-history list (confirmed: `ClientLtvRibbon.tsx:1-8` explicitly says it "adds zero new DB queries," and `client-metrics.ts`'s `getClientLifetimeMetrics` is a pure function over whatever `bookingHistory` it's given). This means **the same dual-use tension as finding #1 exists here too**: if `bookingHistory` is paginated (page-size slice via `.range()`) to bound the booking-history list rail, the LTV ribbon's lifetime totals and 12-month sparkline would silently become wrong (reflecting only one page of bookings, not the client's whole history). Phase C needs two separate reads for this page: a bounded one for the list rail, and either the existing unbounded one (kept, since it's naturally small per-client) or a lightweight aggregate for the ribbon — not one `.range()`'d query serving both.

### 4. Enquiries — C-09's filter move, and what "one `.range()` + the bar" misses

**Confirmed:** filters (status/source/assignedStaff/fromDate/toDate/q) are genuinely server-side SQL predicates in `enquiries-data.ts:125-148` (`.eq`/`.not`/`.in`/`.gte`/`.lte`/`.or` with proper `.ilike` escaping), folded into the cache key. C-09 kept this promise.

But the brief's "one `.range()` + the bar" (§2.3) understates the remaining work:

- The page never calls `getEnquiriesPageData` with `limit`/`offset` today (both calls, `page.tsx:155` and `:168`, omit them) — wiring the existing params + `PaginationBar` covers the simple default-sort case.
- **Sort is not server-side.** `newest`/`oldest`/`name`/`activity` is a JS `.sort()` applied *after* the fetch (`page.tsx:181-195`); the SQL query only ever orders `created_at desc` (`enquiries-data.ts:124`, hardcoded). Once the fetch is capped via `.range()`, sorting only the current page's rows in JS would silently produce a wrong *global* order for "oldest"/"name"/"activity" — each page would be internally sorted but pages would not chain correctly. `sort` needs to become a real parameterized SQL `.order()` inside `enquiries-data.ts` before pagination is safe for three of the four sort modes.
- **Tab badge + at-a-glance stats need the same restructuring bookings gets, but the brief doesn't call it out for enquiries.** `newCount` and the today/week/month/conversion stats (`page.tsx:162, 206-219`) are computed by scanning the full unfiltered fetch in JS — the same shape §2.3/§5.6 flag for bookings' chip counts (converting them to count-only head queries). Without an equivalent conversion here, either the stats-feeding fetch stays unbounded (defeating the point of pagination) or, if it's also capped, the stats become wrong (reflecting a page, not the whole pipeline).

So the true remaining work is three items, not one: (i) wire `limit`/`offset` + `PaginationBar` (the brief's expectation), (ii) move `sort` into SQL `.order()`, (iii) convert tab-badge/at-a-glance stats to count-only aggregate queries. (i) is simple; (ii) and (iii) are real, currently-unplanned gaps.

### 5. Search — server-side or in-memory? Composes with `.range()`?

- **Clients:** in-memory only. `matchesSearch` (`page.tsx:76-90`, matches `full_name`/`phone`/`email`) runs over the full unfiltered client array; no `.ilike()` anywhere in `clients-list-data.ts`. Does **not** compose with `.range()` today, for the same reason as filters/sort in finding #1 — search must run before paging over the whole set. Needs to move to SQL `.ilike()` (the codebase already has the escaping pattern to copy, e.g. `privacy-data.ts`'s `escapeLike`) before `.range()` is safe.
- **Enquiries:** already server-side. Real `.ilike()` via `.or()` (`enquiries-data.ts:138-148`), properly escaped (`escapeLike`, `quoteOrValue`), part of the cache key. This is the one piece of this whole inventory that already composes cleanly with `.range()` — both are independent calls in the same Supabase query-builder chain.

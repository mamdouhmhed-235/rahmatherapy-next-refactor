## Roles diagnosis (the Owner's named example)

**1. Where does the height actually come from?**

It does **not** come from `roles/page.tsx` (the list). `RoleListRow` (`roles/page.tsx:245-374`) renders one compact summary row per role — a letter token, name, 0-2 status badges, a one-line truncated description (`line-clamp-2`), the DB role slug, and a counts cluster (permissions/staff/activity) that collapses to a single chevron-adjacent line on desktop and a small stacked block on mobile. No per-permission detail is rendered inline on the list page. With 5 roles today (realistically 5-15 over 5 years — roles are hand-created by an owner, not user-generated data), this page cannot sprawl regardless of permission-catalog size.

The height driver is the **`[roleId]` detail page's permission matrix** (`roles/[roleId]/page.tsx:250-321`), and specifically the fact that it renders **every active permission** (`allPermissions`, fetched with no limit at `:93-98`) as a `PermissionRow` (`PermissionRow.tsx`), one row per permission, for whichever role you're viewing. Production data: 39 active permissions across 11 categories (`clients 10, bookings 7, reports 6, staff 5, emails 3, system 2, availability 2, settings 1, audit 1, privacy 1, services 1`). Visiting the Owner role (39/39 granted) renders all 39 `PermissionRow` items grouped into 11 category sections. Each `PermissionRow` (`PermissionRow.tsx:136-267`) carries: a name, up to two badges (scope + risk-level), an optional description paragraph, a mono permission-name line, a `Switch` with a status label, plus off-screen confirm-dialog markup — roughly 15-20 DOM nodes per row. **The multiplier is 1 role × up to 39 permissions × ~11 category headers**, not roles × roles.

**2. What is the real data volume?**

Measured 2026-08-03 (SELECT-only): 5 roles, 39 active permissions (11 categories), 94 total `role_permissions` grants (Owner 39, Admin 32, Therapist 12, Booking Coordinator 11, Inactive 0). So the worst-case single-page render is **39 permission rows** (viewing Owner), not 5×39=195 — the list page never renders the matrix, and the detail page only ever shows one role's matrix at a time.

**3. What structure already exists that must be preserved?**

Both the "sprawl" and its fix already exist in the current code (this predates this redesign pass — no recent commit touches these files beyond a global `text-white` → `--admin-on-primary` sweep and mojibake fixes; the structure is original):

- **List page** (`roles/page.tsx`): tier grouping via `groupByTier`/`TIER_LABEL` (`:78-99`, rendered `:169-191`) splitting roles into "Privileged" (Owner/Admin) and "Operational" sections with a heading only shown when both tiers are present (`showTierLabels`, `:144`); and an **inactive-role disclosure** — a native `<details>`/`<summary>` element (`:198-225`) that hides inactive/suspended roles behind a "Show/Hide" toggle with a count badge, rather than listing them inline.
- **Detail page** (`roles/[roleId]/page.tsx`): permissions are grouped by `category` with **sticky, backdrop-blurred section headers** showing the per-category count (`:281-298`); the whole matrix sits inside a **height-capped scroll container** — `max-h-[70vh] overflow-y-auto pr-1 lg:max-h-[min(72vh,720px)]` (`:280`) — so the permission list scrolls *within* its panel and never expands the outer page frame; and a full **filter strip** (`PermissionsFilterStrip.tsx`) lets the operator narrow by category, risk level, granted-only, or free-text search, with a mobile bottom-sheet variant and a desktop inline panel.

**Phase E must preserve all of this** — the tiered grouping, the inactive `<details>` disclosure, the category-grouped sticky headers, the internal scroll cap, and the filter strip. None of it should be re-derived from scratch.

**4. Concrete recommendations for Phase E Step 13**

Given the above, my recommendation is that Phase E Step 13 for the roles surfaces should be scoped as **verify-and-polish, not rebuild**:

- Treat both `roles/page.tsx` and `roles/[roleId]/page.tsx` as **VERIFY-ALREADY-IMPLEMENTED** against the brief's §2.5 goals (tighter density / grouping / disclosure / bounded height) — the structure described above already satisfies "never expands past the page frame," "grouping," and "disclosure." This inventory pass is code-only (no browser was opened); Phase E's own step should do the actual before/after screenshot proof at 375 and 1280 called for in acceptance criterion 6, since that hasn't been visually verified by anyone yet as far as this inventory can confirm.
- The one genuine gap: the detail-page permission fetch itself (`page.tsx:93-98`) has no `.limit()` — harmless at 39 rows, but if the permission catalog is expected to keep growing indefinitely (unlikely — it's a dev-curated catalog, not user data), a soft ceiling or a note that this is intentionally unbounded-but-static would close the loop. Not urgent.
- Do **not** touch `CreateRoleSheet.tsx` or `DangerZonePanel.tsx` — both are forms/action panels with no list-rendering surface (confirmed by reading both in full).

## The two significant findings for the Phase A checkpoint

1. **`services/page.tsx:118-120`** — the "In use" badge/usage-count support query fetches **every row of `booking_items` with no filter and no limit**, purely to build a per-service count via in-memory `Map` reduce. `booking_items` scales with bookings (the brief's own §1.1 table projects bookings at ~10-15k rows in 5 years; `booking_items` is at least 1:1 with bookings, likely higher for multi-service visits). This is the exact "hidden performance cliff nobody sees yet" pattern the brief calls out for `bookings/page.tsx` (§1.2) — except here it's hiding underneath a *static, ≤30-row* services page, which is why it wasn't on the brief's known list (§1.1's code audit only names `bookings/page.tsx`, `clients/page.tsx`, `enquiries`, `emails/page.tsx`, `privacy/page.tsx`, `operations/page.tsx`). **Fix is a query-shape change (SQL aggregate/count-by-service), not a pager** — there is nothing to paginate on a page that renders 5-30 services.

2. **`availability/page.tsx:124-131`** — `BlockedDatesManager` and `AvailabilityOverridesManager` both fetch their full tables with no limit and render every row as a full card in an unbroken list, with no pager, cap, or disclosure. Both tables read `0` rows in production today, which is exactly why this is easy to miss — but a realistic clinic will accumulate 50-150 blocked dates and 25-100 hour adjustments over 5 years (bank holidays, Eid, staff training days, ad hoc closures/adjustments), and both currently have zero structure to keep the Availability tab's height sane at that scale. The brief explicitly warned this agent to check availability "carefully" as something "easy to overlook as config" — this is that case, confirmed by reading the code and the production row counts.

Both findings should be surfaced to the user at the Phase A checkpoint per brief §2.1, since the brief's own expected-surprises list does not anticipate either.

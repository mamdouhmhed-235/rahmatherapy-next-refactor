## Extra-depth findings (per assignment)

### 1. Privacy: queue vs. notes rail (the exact audit-conflation)

**Confirmed at HEAD, independently, with file:line evidence:**

- **Request queue** (`client_privacy_requests`) has never carried a `.limit()`/`.range()`:
  - Today (`privacy-data.ts:124-129`): `.from("client_privacy_requests").select(...).order("created_at",{ascending:false})` — no cap. `.range()` is only appended at `:144-147` `if (limit !== undefined)`, and both call sites in `page.tsx` (`:301-305`, `:310-316`) omit `limit`/`offset` entirely.
  - Pre-C-09 (verified via `git show 9b53902^:src/app/admin/privacy/page.tsx`, lines 224-231): the identical query, inline in `page.tsx` at the time, also had no `.limit()` — only `.order("created_at",{ascending:false})`.
- **Sensitive-notes rail** (`client_notes` where `is_sensitive = true`) is the one that carries the `.limit(25)`:
  - Today: `privacy-data.ts:153-161`, `.limit(PRIVACY_NOTES_LIMIT)` (`PRIVACY_NOTES_LIMIT = 25`, line 44).
  - Pre-C-09 (same `git show`, lines 232-240): `.from("client_notes")...eq("is_sensitive", true)...limit(25)` — the same 25-cap, on the same table, in the same pre-existing shape.

**Conclusion: the pre-flight's correction is right, and the original 2026-07-16 audit's "privacy capped at 25, no pager" claim was wrong** — it described the notes rail's cap as if it applied to the whole `/admin/privacy` surface, when the request queue (the GDPR-facing surface) has *never* had any bound, at any point in this repo's history that I checked. These are two separate regions (rows 1 and 2 above) with two separate verdicts (`paginate` vs. `cap+view-all`), exactly as the assignment instructed they must be kept separate.

**Does hitting the 25-cap on the notes rail silently hide notes?** Yes. `PRIVACY_NOTES_LIMIT` bounds `client_notes` (sensitive only), newest-first, practice-wide (not per-client). Once more than 25 sensitive notes exist across all clients, the 26th-oldest and beyond simply never load — there is no total count shown (badge reads `Last ${notes.length}`, i.e. just the count of what was fetched, which is capped at 25 so it never reads above 25) and no link anywhere to see older ones. The empty-state and badge copy ("last 25 client records") is the only signal to the operator that this is a window, not the whole set.

### 2. Staff: the C-09 handoff claim, verified

**Confirmed at HEAD:** `staff-list-data.ts:54-61` (in-file comment, C-16 pagination note) states the directory read "deliberately exposes no limit/offset" because `staffProfilesFrom`'s return type is FPM-preserved. I verified this independently by reading `team-access.ts:37-47`: the `StaffProfilesQueryBuilder` type's method surface is exactly `eq`, `order`, `maybeSingle` (plus the `PromiseLike` it extends) — there is no `.range` or `.limit` method on the type at all, so the C-09 handoff's claim is accurate, not stale.

**Concrete meaning for Phase C/D, stated plainly (not hedged):** `/admin/staff` is **already-correct** today, and the reason is business reality, not code luck — staff headcount (12 rows, realistically tens even at aggressive 5-year growth) does not scale with bookings/clients volume the way the "fast" surfaces do. It needs no pagination work. The one thing that must be decided *consciously* if this surface is ever revisited: `page.tsx:228-246`'s in-memory `matchesQ`/`matchesWorkload`/`matchesOnboarding` filters currently run over the *entire* scoped-and-server-filtered set. If a future change ever adds `.range()` to `staffProfilesFrom` without first widening the builder type to carry a real `.ilike` for `q` (and moving workload/onboarding to real predicates or accepting they'd need a schema change), those three filters would silently filter only the current page and under-report matches — a correctness bug, not a performance one. That's a "if X, then Y" flag for whoever picks this up later, not a recommendation to do anything now.

### 3. `[staffId]` detail/performance: does it render unbounded lists?

- **Assigned bookings** (row 5): capped at query-level (16, by `created_at`) then capped again in-memory for the past bucket (8). Growth here is real and per-staff — dividing the whole-practice bookings growth (10-15k in 5 years, per the brief's own table) by headcount (~12-20) projects **roughly 500-1,250 assignments per staff member by year 5**, honestly stated. The existing "Show all assignments" link only reaches the *upcoming* bookings view (`view=upcoming`), not past — so a staff member's older assignment history has no reachable view-all path once it falls outside the 16-row cap. This is the one concrete gap in this row I'd put on the punch list.
- **Audit history** (row 6): capped at 8, but genuinely reachable in full via the already-correct cursor-paginated `/admin/audit?target_type=staff&target_id=...` link. No gap.
- **Sibling staff / weekly availability pattern** (rows 7, 8): both bounded by nature (headcount, day-of-week respectively). No gap.
- **Blocked dates / one-off overrides** (rows 9, 10): genuinely unbounded queries, contained today only by a closed-by-default disclosure that itself has no internal cap. Low priority given near-zero current counts, but a real 5-year-honesty gap, flagged for conscious decision rather than left as a silent default.
- **Performance sub-route**: no direct list query of its own; delegates to the shared reporting pipeline, which is out of this plan's scope and off-limits to touch (RECON §5 + brief §12).

### 4. Password requests / password reset

- **`/admin/account-password-requests`** (row 12) is the real list surface here: slow-growing (staff-only, bounded by headcount × forgetfulness), but genuinely unbounded today — full-table fetch, in-memory status-tab filtering, and (unlike privacy/staff) not even cache-wrapped. Old rows (especially `expired`/`rejected`/`approved`, which never get cleaned up) have no lasting operational value once resolved, but they do have audit/compliance value (who approved/rejected what, when) — so the right treatment is a pager, not deletion, consistent with the brief's "no archival/retention" non-goal (§12).
- **`/admin/password-reset`** (row 13) is not a list surface at all — it's the *requesting* staff member's own single pending-request state machine, tracked by cookie + a single `.eq()` lookup. Nothing to paginate; recorded explicitly as "no region," per the assignment's instruction to decide every surface consciously rather than skip silently.

## 2 — Prose findings

### 2.1 The big one: `reporting.ts`'s shared `getReportData` is the common unbounded-query root cause for calendar, dashboard, and reports alike

`reporting.ts:270-329` (`getReportData`) is on the SUBAGENT-RULES untouchable list, and is used by:
- **Calendar** — `calendar-data.ts:84-125` calls it directly for every calendar page load.
- **Reports** — `reports-data.ts:45-77` (`fetchCachedReportData`) calls it directly.
- **Dashboard** — `dashboard-data.ts` does **not** call `getReportData` (it has its own parallel implementation, `getDashboardDataInner`, lines 200-319), but that implementation has the exact same shape: `getEnquiries` (`dashboard-data.ts:519-536`), `getEmailEvents` (541-559) and `getOperationalEvents` (561-579) all omit `.limit()` entirely, and `getClients` (449-472) omits it for the Business/Coordinator "team" scope (only the Therapist/"Mine" scopes restrict via `.in("id", linkedClientIds)`).

Of `getReportData`'s nine parallel queries, only **one** — `bookings` (`reporting.ts:286-293`) — carries a bound (`.gte`/`.lte` on `booking_date`). The other eight (`booking_assignments`, `booking_items`, `clients`, `staff_profiles`, `staff_availability_rules`, `enquiries`, `email_delivery_events`, `operational_events`) read the entire table, every time, with no date filter and no `.limit()`. Six of those eight then get filtered down in-memory to whatever's relevant (`reporting.ts:338-382`).

At today's row counts (bookings 15, clients 15, enquiries 3, email_delivery_events 43, operational_events 1 — measured 2026-08-03) this is invisible. At the brief's 5-year projection (clients 3-6k, enquiries 1-3k, email_delivery_events 50-100k, operational_events "tens of thousands"), every calendar view, every dashboard load, and every reports page render would pull 50-100k+ email delivery rows into memory just to compute a handful of counts and top-8/top-5/top-3 lists. This is squarely the "aggregate is not the same as bounded" case the brief's checkpoint asks to separate: the **renders** on top of this data (rows 1, 2, 5, 13-16 in the table) are almost all correctly capped; the **query** underneath every one of them is not.

Because `reporting.ts` core exports are explicitly untouchable for this dispatch, I am not proposing a fix — only recording that the bound does not exist, per the assignment's ask to "establish whether those reads are bounded" for `email_delivery_events`/`operational_events`: **confirmed not bounded**, and the same is true of `clients`, `enquiries`, `booking_assignments` and `booking_items`.

### 2.2 Three instances of "bounded query defeats a wider-window in-memory filter" (the `weekCount` shape), beyond the one already logged

The dispatch names one known instance (Therapist "open to claim", `weekCount`, already logged — not re-reported here). Reading the surrounding code turned up the same shape recurring:

- **Row 7** — `nextSevenDays` (`page.tsx:151,170-176`) computes a 7-day-forward filter over `data.bookings`, which on a plain `/admin/dashboard` visit (no `range`/`from`/`to` in the URL) is bound to `today..today` (`page.tsx:79-89`). `BusinessDashboard.tsx:262` and `CoordinatorDashboard.tsx:427` both feed `nextSevenDays.length` into a UI element unconditionally labelled `"next 7 days"` (`dashboard-cards.tsx:335`). On the default view this reads **"0 in the next 7 days"** even when bookings exist next week. Notably, the same `nextSevenDays` value is *also* used for `ScheduleGapStripe` (row 4) — and there the developers caught the mismatch and passed `rangeLabel="Selected range"` instead of the default "Next 7 days" copy (`CoordinatorDashboard.tsx:325-331,455`). The header stat and `TodayAtAGlanceCard` prop were not given the same treatment.
- **Row 8** — `getRecentClientsForTherapist(data, today, 30, 6)` (`TherapistDashboard.tsx:149`) promises "last 30 days" (its own doc comment and the UI copy at `RecentClientsStrip.tsx:53`), but `data` is the same page-level, filter-bound `getDashboardData` result — `today..today` by default. No second, wider-window fetch backs this call (contrast with the working fix at `page.tsx:278-287`, which *does* add a second `getDashboardData` call with `claimableWindowFilters` for the "open to claim" list).
- **Row 9** — `myUpcoming`/`myNextAppointment` (practitioner-mode mini list, `page.tsx:372-386`) filters `data.bookings` for `booking_date >= today`, same array, same default bound. Flagged at lower confidence — I traced the filter shape but not every downstream consumer, so this is a "likely same pattern" note rather than a confirmed defect.

None of these are unbounded-*growth* problems in the pagination sense (they don't get slower as the table grows) — they are correctness bugs that happen to share the exact "the array was already narrowed upstream, so a filter expecting a wider set silently returns less than intended" shape the assignment asked me to watch for. Flagging for the record; not in scope for me to fix (read-only dispatch, and outside my assigned write surface even if it weren't).

### 2.3 Calendar's date-window bound is real and correctly enforced

Read `calendar/page.tsx` end to end for the bound-enforcement logic (not just the comment in `calendar-data.ts`): a hand-typed `to` param that would produce a range longer than `RANGE_SOFT_CAP_DAYS = 31` (`calendar/page.tsx:86`) is caught and the view snaps back to month (`calendar/page.tsx:213-215`); month view itself is always a fixed 6×7 = 42-cell grid (`buildMonthGridDates`, lines 118-121) regardless of the calendar month's actual length; week view is always exactly 7 dates; day view is always exactly 1. There is no "show all" mode and no code path that lets a request reach the database with an unbounded date range — every view resolves to a concrete `filters.from`/`filters.to` before `getCalendarPageData` is called (`calendar/page.tsx:238-254`). The **bookings** query itself is therefore correctly verdicted `already-correct`, named bound: **date-window, capped at 31 days for range view / 42-day fixed grid for month view**. The caveat is entirely in §2.1/§2.2 above (the same call's other five table reads), not in the calendar's own date-bounding logic.

### 2.4 Admin search is bounded, contrary to the brief's stated concern

The brief flags admin search as "not in the brief's expected table at all" and worries about an unbounded global search. Reading `search-actions.ts` directly: both `searchBookings` (`.limit(8)`, line 78) and `searchClients` (`.limit(8)`, line 132) cap at the database, and the merged, cross-type result is sliced to 12 (`search-actions.ts:160`). This is one of the best-bounded surfaces in the inventory — verdict `already-correct`. The one gap is a coverage gap, not a growth-bound gap: enquiries are not searchable at all (only bookings and clients), which is presumably intentional (enquiries has its own list page) but is not addressed here since it's not a pagination concern.

### 2.5 Nav notification bell is bounded, with a minor order-then-limit caveat

`nav-notifications.ts` caps every one of its ~10 queries with an explicit `.limit()` (10 for most result categories, 50/20 for two intermediate id-lookup queries at lines 436 and 479). Verdict `already-correct`. The two intermediate queries lack an `ORDER BY` before their `LIMIT`, which is a soft growth risk (not a confirmed defect): as a therapist's all-time assignment count, or the practice's all-time open-claimable-assignment count, grows past 50/20, the specific rows returned are not guaranteed to be the most relevant ones for the downstream date/status filter. Noting for completeness; this is materially different from — and much less severe than — the unbounded, no-limit-at-all queries in §2.1.

### 2.6 Dashboard stripes and reports aggregates: which components, confirmed

Per the brief's ask to confirm which components the DO-NOT-TOUCH "dashboard stripes (top-N by design)" and "reports aggregates" actually are:

- **Dashboard stripes** = `UrgentAttentionPanel`/`PendingBookingsStripe` (top 5 + paginated modal), `ActiveEnquiriesCard`/`EnquiriesTodoStripe` (top 2), `ClaimQueueStripe` (top 5), `ScheduleGapStripe` (top 5), `OperationsHealthCard` (4 fixed rows), `TodayAtAGlanceCard`'s appointment lists (top 5). All confirmed top-N-capped at render time — rows 1-6 above.
- **Reports aggregates** = `WorkloadStaffRow` (top 8, static/staff-count-bound), the two service-performance sections (top 8 each), `staffRevenue` (top 8), `InsightsStripe` (≤3). All confirmed top-N-capped — rows 13-16.

Both groups are correctly named "already bounded by design" **at the render layer** and a future phase should not mistake them for unbounded lists needing a `PaginationBar`. The distinct, separate finding is §2.1: several of these renders sit on top of unbounded queries, which is a query-shape problem to fix in `reporting.ts`/`dashboard-data.ts`, not a render/pagination problem to fix in the stripe components themselves.

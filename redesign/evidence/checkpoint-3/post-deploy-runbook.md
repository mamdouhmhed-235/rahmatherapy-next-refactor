**What `MAINTENANCE_MODE` actually gates** (read from `src/app/(public)/layout.tsx:5,22,28-29`): it is a single boolean read once in the public route-group layout that wraps every customer-facing page.
- `true` → renders `<MaintenanceBanner />` at the top of every page, renders `<MaintenanceModal />` (a one-per-session dialog telling visitors *"Our website isn't quite ready yet"* with phone/email as the only contact method — `src/components/shared/MaintenanceModal.tsx:36-63`), and **does not mount `<BookingExperienceLoader />` at all** — the real booking widget never loads.
- `false` → normal site: no banner, no modal, the real booking flow is live and bookable.

**The real consequence if `false` ships:** this is not cosmetic. It is the switch between "the public site cannot take a real booking" and "the public site is fully live and bookable by real customers." Because the committed HEAD value is already `true`, the actual risk is narrower than "restore it" implies — the risk is the **local uncommitted `false` getting swept into a commit** before the push (e.g. a broad `git add -A`, or a future session staging it without noticing). **Before the push that triggers the deploy:** confirm `git status -- src/lib/maintenance.ts` still shows it as an unstaged modification (i.e. it was never `git add`ed), or have the Owner explicitly discard the working-copy edit so the pushed tree matches HEAD's `true` exactly. Either way this is a manual Owner action — no agent may stage, commit, or revert this file (SUBAGENT-RULES.md prohibition 3).

The final programme report must state this file's state at push time (`OWNER-ACTION-BACKLOG.md` row 14).

| Activation | Trigger | Customer-visible consequence |

### As soon as possible after deploy — create these fixtures early, the checks below need real elapsed time

**Before the next four checks:** create the C-02 recurring-series fixtures **as early as possible after the deploy** (they can also be created as part of the general, non-deploy-gated Owner sweep already listed in `OWNER-ACTION-BACKLOG.md` row for C-02 items 1–7 — reusing the same fixtures here saves a second round of fixture creation). Reasoning, derived from reading `src/app/api/cron/extend-recurring-horizons/route.ts` (not stated in any progress file, so treat the timing as an estimate to confirm empirically rather than an exact figure): the create RPC sets a new series' `horizon_through_date` to `anchor + 83 days` (12 weeks − 1 day) at creation, and this cron advances that boundary by exactly one calendar day per nightly run once the anchor date has passed. Working through the arithmetic, a series' *next* not-yet-materialised occurrence (the 13th weekly / 7th fortnightly visit) enters the extension window roughly **2–3 nights after the series' anchor (first-occurrence) date** — not on the very first post-deploy night, and not a full cadence period later either. Confirm actual timing via `audit_logs.action_type = 'recurring_series_extended'` rather than assuming a day count.

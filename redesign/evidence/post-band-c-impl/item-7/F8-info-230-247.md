# F8 — Focus / Info Blues

2 distinct literals, 3 occurrences. Small family; effort spent on proof, not volume.

## Literal 1 — `oklch(47% 0.095 230)` (2x, both in `src/components/ui/input.tsx`)

Both occurrences are the fallback arm of `var(--admin-focus, oklch(47%_0.095_230))`:

```
src/components/ui/input.tsx:36  "focus-visible:border-[var(--admin-focus,oklch(47%_0.095_230))]",
src/components/ui/input.tsx:38  "focus-visible:ring-2 focus-visible:ring-[var(--admin-focus,oklch(47%_0.095_230))]/30",
```

### The question: does the fallback ever actually paint?

`--admin-focus` exists in tokens.css but its light value is `#a14820` — a burnt orange —
while the fallback baked into `input.tsx` is `oklch(47% 0.095 230)`, a blue. These are not
the same colour with different syntax; they're different hues entirely. If the fallback ever
fires, a user sees a blue focus ring where the design system says orange.

CSS custom-property fallback (`var(--x, fallback)`) only evaluates `fallback` when `--x` is
**not defined** (or invalid) at the point of use. It is not conditional on theme, on which
value the property currently holds, or on anything else — MDN / CSS Custom Properties spec:
the fallback is used "if the custom property... is invalid or not yet declared." So the
question reduces to: is `--admin-focus` unconditionally declared, with a valid value, for
every element `<Input>` can render at?

Traced the declaration chain:

1. **`src/styles/tokens.css:98`** — `--admin-focus: #a14820;` is declared inside the bare
   `:root { ... }` block, with **no selector gate** (`:root` alone, not
   `[data-theme="…"]`). `:root` matches `<html>`, and `<html>` exists on every page of this
   app, unconditionally. There is no code path where the `:root` rule fails to apply.
2. The theme blocks (`[data-theme="dark"]`, `[data-theme="light"]`, `@media print`) each
   *redeclare* `--admin-focus` (lines 394, 529, 645) with equal specificity — they don't
   remove or gate the `:root` declaration, they override it when they also match. Whichever
   one wins, the property still resolves to a valid colour (`#a14820` or
   `oklch(76% 0.145 55)`), never to "undefined."
3. **`src/app/globals.css:4`** — `@import "../styles/tokens.css";` is unconditional, at the
   top of the global stylesheet.
4. **`src/app/layout.tsx:5`** — `import "./globals.css";` in the *root* layout, which wraps
   every route in the app (both `src/app/admin/**` and public routes like
   `/booking/manage`), confirmed by reading the file. There is no per-route layout that
   opts out of the root layout's CSS.
5. No `@property --admin-focus { ... }` registration exists anywhere in `src/` (checked —
   zero matches), so there's no syntax-restricted custom property that could make the
   declared value register as "invalid" and force a fallback. `#a14820` and
   `oklch(76% 0.145 55)` are both trivially valid `<color>` values under the default
   (untyped) custom-property registration.
6. tokens.css itself already documents this exact conclusion for this exact component, in
   the comment block above the theme selectors (lines ~304-309):
   > "`input.tsx` — every `<Input>`, unconditionally (surface-input, border-form, body,
   > text-muted, focus, radius-control). **The var() fallbacks never fire, because :root
   > always defines these.**"

   That note was written independently of this task (it documents *why* the theme-scoping
   selector lives on a wrapper div rather than `<html>`, using Input's fallbacks as the
   illustrating example) and it lines up exactly with the chain traced above. Two
   independent derivations, same answer.

### Verdict: provably a no-op

`--admin-focus` is declared at `:root` with no gating selector, resolves to a valid colour
on every element in every document this app renders (admin and public alike, including
`/booking/manage`), in every theme, in print. CSS var()-fallback only fires when the
referenced property is undefined/invalid — never the case here. **The blue fallback
literal can never paint a pixel.** Removing it is a byte-for-byte-safe no-op for anything a
user can see.

### Decision: `drop-dead-fallback`

No new token. Strip the fallback so the site reads `var(--admin-focus)` (the ambient value,
`--admin-focus` itself, is untouched — this family isn't minting or editing that token).

Sites:

| file:line | find | replace |
|---|---|---|
| `src/components/ui/input.tsx:36` | `focus-visible:border-[var(--admin-focus,oklch(47%_0.095_230))]` | `focus-visible:border-[var(--admin-focus)]` |
| `src/components/ui/input.tsx:38` | `focus-visible:ring-[var(--admin-focus,oklch(47%_0.095_230))]/30` | `focus-visible:ring-[var(--admin-focus)]/30` |

## Literal 2 — `oklch(60% 0.08 247)` (1x, `src/app/admin/clients/page.tsx:1121`)

```
className={`group relative flex min-h-[56px] items-center gap-3 rounded-[var(--admin-radius-control)] border-b border-b-transparent px-3 py-2 transition-colors duration-150 ease-out hover:bg-[var(--admin-hover-mist)] hover:border-b-[oklch(60% 0.08 247)] focus-within:bg-[var(--admin-hover-mist)] md:gap-4 md:px-4 ${rowOpacity}`}
```

This is the client-list row (`ClientListItem`-equivalent `<li>`): a hover-only bottom-border
accent that appears together with the `--admin-hover-mist` hover background. No existing
token is byte-identical to this light value (confirmed against the full 94-token table in
TAIL-CENSUS.md).

**Source oddity, noted but not "fixed" as a separate change:** the bracket expression uses a
literal space (`oklch(60% 0.08 247)`), not the usual Tailwind underscore escaping
(`oklch(60%_0.08_247)`). Tailwind's static content scanner treats runs of whitespace as
candidate boundaries, so as authored this string cannot produce one matching utility class —
the rendered `class=""` attribute gets three space-split, meaningless tokens
(`hover:border-b-[oklch(60%`, `0.08`, `247)]`), none of which match compiled CSS. This
`hover:border-b` effect is very likely already inert in production, independent of dark
mode. Replacing it with `var(--admin-hover-mist-border)` (no internal whitespace) incidentally
produces a syntactically valid single utility and would make the effect start rendering for
the first time — flagging this so it's a known, deliberate side effect of the mechanical
edit, not a surprise. Not treating this as license to change anything beyond the literal
substitution itself.

**Existing hover+border pairing precedent, and why it doesn't apply here:** most other
`hover:bg-[var(--admin-hover-mist)]` sites in the codebase (e.g.
`ClientRowMenu.tsx`, `roles/[roleId]/page.tsx:358`, `[clientId]/page.tsx:1145`,
`ManualBookingForm.tsx:1557`) pair it with `hover:border-[var(--admin-primary)]/40` — reusing
an existing token at reduced opacity rather than a bespoke colour. I checked whether that
pattern could be reused here instead of minting a token: alpha-compositing `--admin-primary`
(`#0f5e8e`) at 40% over the light `--admin-hover-mist` background (`#e5f2ff`) computes to
approximately `#8fb7d2`, but the literal actually in the source resolves to `#5885ae` — a
visibly different, darker/more saturated colour. Reusing `--admin-primary`/40 would move
light-mode pixels, which rule 2 forbids. This site's literal is a genuine one-off (drift from
the more common `--admin-primary`/40 pattern used elsewhere), not a value that happens to
already have a token — so per "one distinct light value = one token," it gets its own pair
rather than being folded into `--admin-primary`.

### Nearest sibling for naming vs. for inversion shape

- **Naming**: extends `--admin-hover-mist` (`--admin-hover-mist-border`) — it is the border
  accompanying that exact background at this exact call site, and "name it for what it
  paints" favours tying it to the fill it decorates over inventing a standalone name.
- **Inversion shape**: NOT modelled on `--admin-hover-mist`'s own shape. `--admin-hover-mist`
  is a large-area background fill and inverts with a full flip (light `95.5%` → dark `27%`,
  pastel-to-near-black) — mechanically scaling that ratio onto a moderate-lightness border
  literal (`60%`) would drop it to ~`17%`, indistinguishable from the dark canvas/panel
  (`17%`/`22%`) it sits on, defeating the point of a visible border. A border needs a
  different inversion philosophy than the bg it sits on.
  Instead modelled on **`--admin-border-form`** (`oklch(55% 0.022 80)` light →
  `oklch(58% 0.018 80)` dark) — same *role* (a non-text-contrast structural border/line that
  must stay visible against both a light and a dark surface without a dramatic flip), and its
  starting lightness (55%) is the closest in the whole token table to this literal's 60%.
  Applying border-form's own ΔL (×1.0545, i.e. +3 points) and Δchroma (×0.818) to the
  literal:
  - L: 60 × 1.0545 ≈ 63.3 → **63%**
  - C: 0.08 × 0.818 ≈ 0.0655 → **0.065**
  - H: held at 247 (every other hue-247 sibling — hover-mist, selected-sky, nav-active-bg —
    keeps hue constant across light/dark; no reason to deviate)

  → dark value: `oklch(63% 0.065 247)`

### Contrast check (computed with the shipped script's own `oklchToRgb`/`contrastRatio`, reused verbatim via `node -e`, not re-derived by hand)

- Light literal `oklch(60% 0.08 247)` → `#5885ae`, vs light `--admin-hover-mist` (`#e5f2ff`):
  **3.4336:1** (clears WCAG 1.4.11 non-text 3:1, the relevant SC for a border/UI-boundary).
- Dark candidate `oklch(63% 0.065 247)` → `#698daf`, vs dark `--admin-hover-mist`
  (`oklch(27% 0.018 247)` → `#1f272f`): **4.3394:1** — rounds to **4.34:1**, comfortably
  above 3:1 and above the light-mode margin (consistent with "more luminance for emphasis in
  dark," even though this token isn't literally a hover-state darken/lighten pair since the
  resting state is `border-b-transparent`, not a coloured border that needs to invert
  direction).

Comment written on the dark declaration: `/* 4.34:1 vs hover-mist */`.

### Decision: `new-token-pair`

New token `--admin-hover-mist-border`:
- `:root`, `[data-theme="light"]`, `@media print`: `oklch(60% 0.08 247)` (byte-identical to
  the literal — same spacing style as every other oklch declaration already in tokens.css).
- `[data-theme="dark"]`: `oklch(63% 0.065 247); /* 4.34:1 vs hover-mist */`

Site:

| file:line | find | replace |
|---|---|---|
| `src/app/admin/clients/page.tsx:1121` | `hover:border-b-[oklch(60% 0.08 247)]` | `hover:border-b-[var(--admin-hover-mist-border)]` |

Suggested placement: immediately after `--admin-hover-mist` / `--admin-selected-sky` in each
block (tokens.css lines ~144-145 in `:root`; the matching lines in the three other blocks),
since it's that family's border companion by both hue and adjacency at its call site.

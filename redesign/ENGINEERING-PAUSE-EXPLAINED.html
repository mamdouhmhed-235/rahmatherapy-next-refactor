Engineering Pause — what each step actually means Plain-English walkthrough of the 6 prompts that resolve your Phase 7 Gate 0 gaps

You're stepping out of the recipe to fix the backend gaps Phase 7 Gate 0 flagged as FAIL. This guide shows — for each of the 6 prompts I gave you — what you actually do, what Claude actually does, what files appear at the end, and when you know it's safe to move on.

The whole thing in 30 seconds

  1. You paste 6 prompts, one at a time, into a fresh Claude Code session. Each prompt does one job and ends with a STOP.
  2. 3 of the 6 are real building work (cron + Edge Function + email-templates table). 1 is doc-only. 2 are verification drills (Sentry + backup).
  3. Several will pause and ask you to confirm things that cost money or touch the production database. Always answer with what you actually want — never "yes" reflexively.
  4. Each step writes one or more files as evidence. You check the files exist before pasting the next prompt.
  5. Total time: ~2-4 hours of your active attention, mostly Steps 2, 3, and 5b. Cheap-budget total: ~$0-$10. Full-Branching budget: ~$25-100.
  6. When Step 6 finishes, Phase 7 can resume cleanly.

What this is and what it isn't

This ISRegular dev work — building features, running migrations, exercising monitoring. No different from any other engineering session.
This IS NOTPart of the Phase 7 recipe. The recipe explicitly says it doesn't build backend; that's why you're stepping out.
Why "pause"?You can't resume Phase 7 until Gate 0 reads PASS. Gate 0 only reads PASS when every BLOCKS-REDESIGN item is HANDLED with evidence.
What "evidence" meansA real smoke-test transcript file in backend-smoke-tests/. A grep count. A Sentry issue ID. Not a paragraph saying "should work."
Why so many STOPs?Each STOP is a chance for you to redirect if Claude misread something. Don't paste the next prompt without reviewing.
What's a "Zone-2 stop"?Claude pauses before anything that costs money, enables Supabase features, or modifies production. You decide each time.

  • Compares against production row counts. They should match.
  • Measures restore time start→finish.
  • Tears down the throwaway target (deletes branch / pauses + deletes project).

  • Updates FINAL-REPORT.md L1-c FAIL → PASS.

What to expect at the end

new evidenceredesign/backend-smoke-tests/backup-restore-drill-2026-05-19.txt

Things that might confuse you

  • "Why is this expensive?" Supabase Branching and separate-project both cost money per hour. Option 3 (local dump) is free but only proves you can restore to local, not to a real Supabase environment.
  • "Do row counts have to match exactly?" They should, within a small delta for rows written between backup-time and restore-time. Big mismatches mean the backup is incomplete.
  • "What if the restore fails?" That's the whole point of the drill — you'd discover it now, not during an actual incident. Capture the failure mode and surface to me.
  • "Is Option 3 really 'fail-equivalent'?" It's the cheapest valid PASS — proves the backup file is good and restorable. It just doesn't prove Supabase-side restore works end-to-end. Acceptable for small teams; weaker for compliance-heavy contexts.
Critical: the tear-down step is non-negotiable. A leftover Branching preview or unpaused throwaway project will keep billing. Verify the target is gone before you sign off.

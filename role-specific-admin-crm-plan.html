Role-Specific Admin CRM Implementation Plan

This plan turns the admin CRM from one owner-style interface into a role-aware business system where every admin-facing page changes by access, data scope, actions, and relevance.

Core Principle Permissions decide actions, scopes decide data, and role-specific UI decides what is relevant.
Standalone Phases Each phase includes enough context, gates, files, checks, and a copyable prompt to send to another model independently.
Execution Safety App code, RLS, browser behavior, and Supabase state must be checked together before any phase is considered complete.

Global Gates For Every Phase

These gates apply to every standalone phase, even if the phase prompt is sent by itself.

Before Editing

  • State assumptions and the exact files you plan to inspect.
  • Run git status --short and do not revert unrelated changes.
  • Inspect the relevant files with rg and direct reads before asserting behavior.
  • Use Supabase MCP for Supabase schema/RLS/permission verification when a phase touches backend behavior.
  • Ask for explicit approval before live destructive data changes, mass updates, storage bucket deletion, or Auth user mutation.

During Implementation

  • Use canonical permissions only. Do not add legacy aliases.
  • Prefer scoped queries over fetching all rows and hiding fields in the UI.
  • Keep role permission bundles in Supabase data; app code may check stable permission slugs but must not hardcode role-to-permission bundles.
  • Do not add staff permission overrides unless the phase explicitly asks for overrides.
  • Do not change historical migrations; add new timestamped migrations only.
  • Do not start a dev server if one is already running. If browser verification is needed, use the already-running http://localhost:3000 unless the user says otherwise.

Before Completion

  • Run the narrowest meaningful tests first, then broader checks when the phase is complete.
  • Run pnpm lint and pnpm build for frontend/admin changes unless impossible.
  • Run pnpm test when tests were added or behavior changed across shared helpers.
  • Run an exact rg check for deprecated permission names in src and scripts.
  • Use Playwright/Chrome DevTools browser checks for role-facing UI phases.
  • Provide evidence: files changed, commands run, role behavior verified, Supabase checks run, and remaining caveats.

Phase 1

Central Admin Access And Scope System

Create one central capability map that every admin page can use for page access, data scope, and visible actions. This is the foundation for consistent role-specific behavior across the CRM.

Files To Inspect First

  • src/lib/auth/rbac.ts
  • src/app/admin/layout.tsx
  • src/app/admin/components/AdminTopNav.tsx
  • src/app/admin/**/page.tsx
  • Existing tests under src, tests, or __tests__; find with rg --files -g '*test*' -g '*spec*'.

Implementation Requirements

  • Create a focused server-only admin access module if none exists, for example src/lib/auth/admin-access.ts.
  • Define page keys for dashboard, bookings, booking detail, calendar, reports, clients, client detail, enquiries, team/staff, roles, role detail, services, availability, emails, operations, audit, privacy, settings, profile, and account requests.
  • Define scope values for all, assigned, own, operational, team_visible, same_gender_team, sensitive_hidden, and none.
  • Define action flags for view, create, edit, assign, claim, export, manage settings, manage roles, manage profiles, approve requests, and view sensitive fields.
  • Use current StaffProfile and permission helpers. Do not duplicate permission resolution.
  • If earlier helpers are missing, implement the minimal helper needed in this phase and cover it with tests.

Hard Gates

  • No legacy permission aliases.
  • No role-name checks for permission behavior except stable identity/display where unavoidable.
  • No page should be left without an explicit access rule.
  • Inactive or missing staff profile must resolve to no admin page access.

Verification

  • Unit tests prove access/scope/action output for all five roles.
  • pnpm test, pnpm lint, and pnpm build pass or any failure is documented as pre-existing with evidence.
  • Run rg "view_reports|manage_clients|manage_users|manage_staff|manage_roles|manage_permissions|claim_bookings|reassign_bookings|view_all_bookings|view_own_bookings|manage_bookings_own|manage_payments" src scripts and confirm no current code references legacy permission slugs.

Risks And Caveats

  • This phase should not redesign pages. It creates the rule layer that later phases consume.
  • Do not solve every page's UI in this phase; only wire enough access guard usage to prove the model works.

Phase 9

Password Change Request Workflow

Allow staff to request password changes and Owner/Admin to approve or reject them through an auditable account request workflow.

Do not store requested passwords in plain text. If users type the exact desired password, store it temporarily encrypted, then clear it immediately after approval, rejection, or expiry.

Files To Inspect First

  • src/app/admin/staff/[staffId]/page.tsx or profile/account page location.
  • src/app/admin/staff/actions.ts and any account/user actions.
  • src/app/admin/roles and src/app/admin/audit patterns for admin review and audit logging.
  • Supabase Auth Admin integration scripts/actions currently present in the repo.
  • Audit log and operational event schema.

Implementation Requirements

  1. Staff submits password change request from their profile/account page.
  2. User types the exact new password they want only if this remains the chosen product flow.
  3. The password payload is encrypted with a server-only key before storage.
  4. Owner/Admin with the approved account-request permission sees pending requests.
  5. On approval, a server-only action uses Supabase Auth Admin API to update the password.
  6. Request is marked approved or rejected and audited.
  7. Encrypted password payload is cleared immediately after approval, rejection, or expiry.

Hard Gates

  • No plain-text password storage in database, logs, errors, client state, or audit logs.
  • Only server-side code may call Auth Admin APIs.
  • Inactive users cannot submit requests from admin.
  • Staff cannot directly change password through this admin UI without approval.
  • Do not expose the requested password to approving admins after submission.

Verification

  • Tests for request creation, approval, rejection, inactive denial, and payload clearing.
  • Manual/Auth verification that approved password actually changes for a test user.
  • Audit row created without storing password value.
  • Supabase MCP verify schema, RLS, and no readable password payload remains after completion.

Risks And Caveats

  • The safest product flow is admin approval followed by a reset link. If exact desired password is mandatory, encryption and clearing are required.
  • This phase mutates Auth users. Use test users first and ask explicit approval before affecting live non-test accounts.
